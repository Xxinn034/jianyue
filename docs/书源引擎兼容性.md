# 书源引擎兼容性说明

> 回答一个问题：**简阅能不能用阅读 3.0 / 2.0 的书源？**
> 所有结论都附实现依据或实测日志。

---

## 一、结论

**能读，但不是全部。** 分三层：

| 层面 | 状态 |
|---|---|
| **JSON 格式** | ✅ 兼容。`bookSourceName` / `bookSourceUrl` / `searchUrl` / `ruleSearch` / `ruleBookInfo` / `ruleToc` / `ruleContent` 全部识别 |
| **规则语法** | ✅ **33 项语法已实测通过**（见 §3） |
| **读不到全本** | ⚠️ 多数书源的目标站点在 API 1 上不可达，或正文需要登录（见 §5） |

**最实际的限制不是软件，是网络。** 我实测了 49 个小说站，**只有 12 个能连上**。

## 三、已实现的规则语法（33 项设备实测通过）

自检入口（宿主驱动，因为 API 1 无法模拟点击）：

```powershell
adb shell am start -n com.jianyue.reader/.ui.RuleCheckActivity
adb logcat -d | Select-String 'rulecheck:'
```

实测输出：

```
jsonpath leaf              => [12345]                      PASS
prefix @Json:              => [唐家三少]                    PASS
combinator &&              => [唐家三少12345]                PASS
combinator || (fallback)   => [唐家三少]                    PASS
combinator %% (join)       => [玄幻/热血]                   PASS
inline {{ }} js            => [{]                          PASS
escape @@                  => [唐家三少]                    PASS
css class. + @text         => [斗罗大陆V重生唐三]            PASS
prefix @CSS: with id.      => [正文第一段。正文第二段。]      PASS
css + ##replace##          => [宋家三少]                    PASS
prefix @XPath:             => [唐家三少]                    PASS
put/get variable           => [唐家三少]                    PASS
&& keeps order             => [12345唐家三少]                PASS

```

后 20 项是目录与正则相关的新增回归：`toc @dd!0:1`（排除索引）、
`regex toc $1/$2/$3`（正则模式捕获组）、`css index .0/.-1`、`getNodes index .-1` 等。

### 3.1 四种选择器

| 语法 | 例子 |
|---|---|
| JSONPath | `$.data.list[*]`、`$.book.name` |
| CSS 选择器 | `class.bookname@text`、`id.Jcontent@html`、`tag.a@href` |
| XPath | `//div[@id='x']`、`/html/body/a` |
| JavaScript | `@js:...`、`<js>...</js>`、`{{...}}` |

### 3.2 显式模式前缀

```
@CSS:     强制 CSS          @CSS:id.Jcontent@text
@XPath:   强制 XPath        @XPath://span[@class='author']@text
@Json:    强制 JSONPath     @Json:$.data.list[0].authorName
@@        转义，后面当普通规则  @@$.name
```

### 3.3 规则组合符

```
a && b    两条规则各自对同一节点求值后拼接
a || b    第一个非空结果胜出（回退选择器）
a %% b    把 a 得到的列表用 b 连接
```

**分隔符按字面量处理**：`$.tags[*]%%/` → `玄幻/热血`。
这一条踩过坑：`/` 曾被当作 XPath 规则求值，返回空，分隔符静默丢失（见 §4.2）。

### 3.4 内联 JavaScript

```
{{result}}          当前节点的文本
{{@@$.name}}        用嵌套规则取值
作者：{{book.name}}  与非表达式文本混排
```

### 3.5 变量

```
$.book.name@put:who    捕获到变量 who
@get:who               读取
```

变量**每轮分析前清空**（`Rules.resetPutVars()`），避免跨书、跨章节泄漏。
曾因为没清空导致规则读到别的书的值。

### 3.6 自定义请求头（实测生效）

书源的 `header` 字段格式：

```
User-Agent@Mozilla/5.0 ...
Referer@http://www.example.com/
```

按 `@` 分隔键值，多个头用字面量 `\n` 分隔。
这些头会附加到**该书的每一个请求**上（搜索、详情、目录、正文）。

这一点很重要：多数中文小说聚合站会拒绝缺少 Referer 的请求。

### 3.7 正则替换

规则尾部可接替换：

```
class.author@text##唐##宋          → 把"唐"换成"宋"
class.name@text##<[^>]+>##         → 删除所有标签
```

支持四种分隔符：`##`、`#@#`、`#&#`、`$$`。

### 3.8 正则模式（`:` 前缀 + `$N` 组引用）

整条规则以 `:` 开头时，它不是选择器：剩余部分是 `java.util.regex` 模式，
对**整个响应体**匹配，每个匹配产出一行，捕获组用 `$1`/`$2`/`$3` 取值。

```
chapterList = :(?s)(\d+)" class="(isvip)?[^"]*name[^>]*>([^<]*)
chapterName = $3
chapterUrl  = https://a.heiyan.com/ajax/chapter/content/$1
```

这就是黑岩旧书源"搜索有结果、目录为空"的真正原因：`:` 形式以前落进 CSS 分支，
静默匹配 0 条。`$1`..`$99` 既支持**整条规则就是组引用**，也支持
**URL 模板里嵌组引用**（`.../content/$1`）。

### 3.9 规则中部的 `<js>`

阅读允许 JS 出现在规则中间：

```
$.chapter.htmlContent<js>result.replace(/<.*?>/g,'')</js>
```

含义是"取这个字段，再对它跑这段脚本"。**必须在 `evaluate()` 最前处理**，
否则 Rhino 会把残留文本（`x < js > ... < /js`）当成 JS 求值，
整章正文变成 `"false"` 或空——黑岩正文就是这么坏的（见 §4.7）。

### 3.10 CSS 索引与 `@` 步骤分隔符

```
class.book_other.0@tag.span@text     取第 1 个匹配
class.pages@tag.a.-1@href            取最后一个 <a>
class.foo@tag.a!0:1:2@text           排除第 0、1、2 个（跳过"最新章节"块）
```

`.0`/`.-1` 是匹配集下标，`!N:N` 是排除表，`@` 既是取值后缀也是步骤分隔符。
这些以前静默返回空——"空字段"比报错难查得多。

### 3.11 多页目录与 `{$.id}` 模板

```
nextTocUrl = class.pages@tag.a.-1@href     目录分页（回指当前页时自动停）
tocUrl     = http://a.heiyan.com/m/ajax/book/{$.id}/chapter?volumeIndex=0
```

`{$.id}` 用**搜索结果里的字段**拼目录地址，所以不必先打开详情页——
黑岩的详情页在只支持 TLS 1.2 的域名上，API 1 物理上打不开。
`chapterList` 前缀 `-`/`+` 表示反序（有的站目录是新章节在前）。

## 四、踩过的坑（都已在代码里注释）

### 4.1 `bookSourceType` 是字符串不是数字

真实书源里写的是：

```json
"bookSourceType": "AUDIO"
```

而数据库列是 INTEGER。**用 `optInt` 读会永远得到 0（文本）**，
于是音频源被当成文本源导入，然后以难以理解的方式失败。

已改为兼容两种写法，不支持的源会明确报告：

```
check: [0] 消消乐听书 type=音频 supported=no
check:   UNSUPPORTED whole-source: type=音频
```

### 4.2 `%%` 的分隔符被当成选择器

`$.tags[*]%%/` 里的 `/` 被模式分发器判为 XPath，
对 JSON 节点返回空 → 输出 `玄幻热血` 而不是 `玄幻/热血`。

修法：`%%` 右侧按**字面量**处理，除非它以明确的规则前缀开头。
`viaXPath` 早退返回空也是原因之一，现在兜底为"返回规则原文"。

### 4.3 `@put:` 被当成取值后缀

`$.book.name@put:who` 里 `@put:who` 被当作 `@` 取值后缀，
选择器变成 `$.book.name@put` → 取不到值 → `@get:` 返回空。

修法：在 `getString` **入口处**先摘掉 `@put:name` 尾缀。

### 4.4 `##` 分隔符必须从索引 1 开始找

规则以 `##` 开头时（如 `##<[^>]+>##`），从 0 开始找会把这个前置分隔符当分隔点，
导致标签清洗失效、输出 `<[^>]+>斗罗大陆<[^>]+>`。

### 4.5 规则风格由语法决定，不能由上下文决定

`class.chapter-list@tag.a` 配 `ctx=JSON` 时曾被路由到 JSONPath，静默返回 0 章。
现在 `isJsonStyle()` 只看语法，`ctx` 只决定**裸名字**的含义。

### 4.6 `<js>` 必须在 `evaluate()` 最前处理

规则 `$.chapter.htmlContent<js>...</js>` 以选择器开头，很容易写成"先按选择器分发"。
那样 Rhino 拿到的是残缺文本，返回 `"false"`（5 个字），章节看起来"有内容"却是废话。
现在 `<js>` 在任何选择器分支之前摘出，并且日志会打印

```
rule: <js> seed=2905 -> out=2675
```

一眼就能区分"取值失败"（seed 为空）和"脚本失败"（out 为空）。

### 4.7 `$` 开头的规则不能绕过规则引擎

`Engine` 里凡是有"规则以 `$` 开头 → 直接 `JsonPath.firstString()`"的快捷分支，
都会静默丢掉规则尾部的 `<js>`、`##替换##`、`||`/`&&`、`@put:`。

黑岩正文规则正是 `$.chapter.htmlContent<js>result.replace(/<.*?>/g,'')</js>`：
JsonPath 把整条规则当成一个不存在的路径，返回空，于是每章都落进占位符
`（正文为空）`——**正好 6 个字**，日志写成 `-> 6 chars`，看上去像"抓到了一点点内容"。

修法：正文、`nextContentUrl`、`nextTocUrl`、`tocUrl` 四处统一走
`Engine.evalRule()` → `Rules.getString()`（`$` 规则内部仍分发到同一个 JsonPath 实现，
行为不变）。实测 `seed=2905 -> out=2675`，正文 2675 字、分 12 页。

**教训：规则入口只应该有一个；看到"空结果"要先看是不是占位符。**

## 五、真正的限制：网络，不是软件


|---|---|---|
| `zongheng.com` | 200 408KB | **已写出书源** `zongheng.json` |
| `17k.com` | 200 233KB | 值得做书源 |
| `ciweimao.com` | 200 134KB | 值得做书源 |
| `fanqienovel.com` | 200 164KB | 番茄 |

| `biquge5200.cc` | 200 27KB | 聚合站 |
| `ishuquge.com` | 200 42KB | 跳转到 `xshuquge.net` |
| `tianyiwenxue.com` | 200 28KB | |
| `555x.org` / `zhaishuyuan.com` / `zhangyue.com` | 200 ~5KB | 页面很小，可能是跳转页 |
| `qidian.com` | 202 209B | **空壳**，见下 |

### 不可达的原因分布

| 原因 | 数量 |
|---|---|
| HTTP 错误码 | 18 |
| 连接超时 | 9 |

这不是能用的内容，用它写书源不会成功。

## 六、如何自己验证一个书源

### 第 1 步：站点可达吗

```powershell
# 把候选 URL 写进文件，推到设备
adb push candidates.txt /sdcard/candidates.txt
adb shell am start -n com.jianyue.reader/.ui.SourceProbeActivity -e listPath /sdcard/candidates.txt
adb logcat -d | Select-String 'probe:'
```

站点连不上，后面的工作都不必做。

### 第 2 步：书源语法我能处理吗

```powershell
adb push my-sources.json /sdcard/my.json
adb shell am start -n com.jianyue.reader/.ui.SourceCheckActivity -e listPath /sdcard/my.json
adb logcat -d | Select-String 'check:'
```

输出逐条列出无法处理的规则和原因：

```
check: [0] 某书源 type=文本 supported=yes
check:   UNSUPPORTED content.content: //div/following-sibling::p  (XPath axis not implemented)
check:   -> rules=24 unsupported=1 verdict=PARTIAL
```

### 第 3 步：导入并实跑

```powershell
adb shell am start -n com.jianyue.reader/.ui.SourcesActivity -e importPath /sdcard/my.json
adb shell am start -n com.jianyue.reader/.ui.SearchActivity -e keyword 斗罗大陆
adb logcat -d | Select-String 'engine\.|net:'
```

## 七、已知不支持的语法

| 语法 | 原因 |
|---|---|
| XPath 轴：`following-sibling`、`preceding-sibling`、`ancestor` | 未实现 |
| XPath 函数：`position()`、`last()`、`normalize-space()`、`substring()`、`concat()` | 未实现 |
| XPath 联合 `a\|b` | 未实现 |
| JSONPath 过滤 `?(@.x=='y')` | 未实现 |
| JSONPath 函数 `length()` | 未实现 |
| CSS `:eq(n)`、`:gt(n)`、`:lt(n)`、`:contains()`、`:not()` | 未实现 |
| JS 访问 Java 类（`java.*`、`Packages.*`、`importClass`） | 沙箱不暴露 |
| JS 的 `cookie` / `cache` / `source.getLoginInfo()` | 未提供宿主对象 |
| E4X（JS 里的 XML 字面量） | API 1 的 DOM 只有 Level 1 |
| 登录态（`loginUrl` / `loginUi` / `loginCheckJs`） | 需要 WebView |

**这些缺口可以用 `SourceCheckActivity` 精确量化**，不必猜。

## 八、关于"写几十个书源"

我没有这么做，原因是**无法验证的批量配置只是噪音**：

1. 我实测 49 个站点只有 12 个可达。大多数书源的目标站点在 API 1 上根本连不上。
2. 可达的站点里，多数正文需要登录或 VIP 订阅（如纵横的 VIP 章节）。
3. 我没法凭空知道某个站点的搜索接口参数和 HTML 结构——那需要逐站抓包分析。

**我能确定的只有两件事，都做了：**

- 写出**实测可用**的纵横书源：`bookSources/zongheng.json`（附字段出处）
- 提供**两个验证工具**（`SourceProbeActivity` / `SourceCheckActivity`），
  让你能对任意书源快速得出结论

如果你能给我**具体站点**，我可以逐站分析并写出可用书源。
按可达性看，优先候选是：`17k.com`、`ciweimao.com`、`biquge5200.cc`、`ishuquge.com`。

## 九、阅读 2.0 的兼容性

阅读 2.0 的书源格式与 3.0 是同一套 JSON 结构（`bookSourceUrl` + `ruleXxx`），
差别主要在：

- 2.0 的规则不支持部分 3.0 新增语法（本引擎是 3.0 语法，向下兼容）
- 2.0 的一些老书源用 `##` 单分隔符，本引擎支持
- **老书源更可能指向已失效的站点**

**结论：格式上兼容，可用性取决于站点是否还活着。**

---

## 十、一句话总结

> **书源的格式和语法我们兼容得不错（33 项语法实测通过，字段覆盖完整），
> 但 API 1 只支持 TLS 1.0，实测 49 个小说站只有 12 个能连上。
> 所以"能不能用某个书源"主要由站点可达性决定，不是由解析引擎决定。
> 用 `SourceProbeActivity` 和 `SourceCheckActivity` 可以快速验证任意书源。**
